## Ordering and duplication findings

- Filenames are chronologically ordered and no timestamp/name is duplicated in the integration branch.
- Migration 11 is now inherited from `main`; rebase did not duplicate it.
- Migrations 12–15 form an explicit chain: versioned rules → eligible POS total → expiration lots → guest claims.
- Customer authorization policies are introduced in migration 5 and the sensitive redemption-code restriction follows immediately in migration 6.
- The production transaction pipeline precedes all digital-sales, guest-claim and remote reconciliation references.
- No enums are created by these migrations.

## `lot_remaining` assessment

PostgreSQL returns `numeric` for `sum(bigint)`, including the window expression used as `cumulative`. The function in migration 14 declares `remaining bigint` but returns `greatest(least(cumulative - consumed, points), 0)` without a cast. The isolated migration adds `::bigint`, directly addressing SQLSTATE `42804` described in its comment. No later integration-branch migration replaces that function, so the defect remains logically present after rebase.

Decision: keep the isolated fix unchanged for now, do not cherry-pick it into the monolithic branch, and validate it against a disposable/local Supabase database. If reproduced, include it as its own migration commit in the loyalty/database replacement PR after migration 14.

## Security review notes

- All foundational/transaction tables enable RLS and revoke broad access; grants and each RPC signature still require execution against a disposable database to prove correctness.
- `SECURITY DEFINER` functions, where present, require review for fixed `search_path`, explicit authorization and revoked `PUBLIC` execution.
- No production migrations were applied during Phase 0.
- Supabase's 2026-07-10 changelog notice requires TypeScript 5+ for future `supabase-js`; this repository uses TypeScript 5.8.2. The 2026 deprecation of Postgres 14 requires confirming the target project database version before rollout.
